# 版本兼容策略

## 支持级别

| 客户端 | 级别 | 要求 |
| --- | --- | --- |
| 1.24e-1.27b | 必须支持 | 每个发布关卡均应在代表性版本上完成联机回归；不得使用区间内早期版本不存在的功能。 |
| 1.31 | 尽力支持 | 可运行、可联机、流程可完成；不得为修复 1.31 独有问题而破坏经典基线。 |
| 2.0+ | 非目标 | 不做发布门槛；能够运行仅视为额外兼容。 |

这里的 `1.24e-1.27b` 指《冰封王座》经典客户端兼容区间，代表版本为 `1.24e`、`1.25b`、`1.26a`、`1.27b`。

## 开发基线

- 地图格式、JASS 和对象数据能力以 `1.24e` 可识别范围为下限。
- 对源自《混乱之治》的关卡，按 `1.24e` 的《冰封王座》规则和对象数据逐项审计；不能假定地图类型转换会自动完成规则适配。
- 使用 `1.24e` World Editor 能识别的地图格式和能力作为保存基线；不得用 1.31 编辑器覆盖主发行文件。
- 只使用经典 JASS/GUI 能力。禁用 Lua、`Blz*` 原生函数、Frame API、24 玩家槽位和其他后期专属能力。
- 生成脚本除结构解析外，必须使用最低目标版本提取的 `common.j`、`Blizzard.j` 和兼容编译器完成语义编译；特别检查经典 JASS 函数声明顺序。
- 导入资源应使用经典客户端支持的格式和路径；避免依赖 1.31 的文件夹地图、自动导入和多语言 `_Locales` 结构。
- WTS 等文本载体必须逐字节检查编码、BOM 和换行，并以对应目标客户端的官方或已知可运行样本为依据；不得把某一关验证过的 BOM 规则无条件推广到所有地图。
- 所有随机、计时器、镜头和选择逻辑都要检查多人同步，避免本地玩家分支改变同步游戏状态。

## 测试矩阵

当前只长期保留以下两个独立客户端/编辑器环境：

| 版本 | 用途 |
| --- | --- |
| 1.24e | 主开发环境、最低兼容边界与地图加载验证 |
| 1.31 | Reforged 之前版本的前向兼容验证 |

每张地图先用 `1.24e` 和 `1.31` 做端点验证。该策略不等同于逐一验证 1.25-1.27；发现疑似中间版本差异时，再临时加入对应版本定位。两个长期环境必须隔离安装，防止启动器或注册表设置相互覆盖。

## 每关回归清单

- 地图能在编辑器中打开，并能在客户端创建局域网房间。
- 至少两台客户端或两个隔离实例可以加入并完成开局。
- 玩家槽位、种族、队伍、颜色和控制权正确。
- 原友方 AI 槽在进入地图时按真人、电脑、空槽和未加入分别选择控制模式，且开局后不再切换；空槽能否运行 AI 必须有目标客户端证据，不能仅检查脚本调用可达。
- 只有原版单人战役的真人可玩槽能够在进图后选择普通或困难；选择完成前不启动原版难度分支、AI、计时器或过场，选择后所有客户端的 `GetGameDifficulty()` 结果一致。
- 任务文本、对白、声音、模型和图标没有丢失。
- 过场播放/跳过对所有玩家一致，结束后控制权正确恢复。
- 联盟菜单中的共享控制必须双向开关验证，并在至少一次过场正常结束和一次跳过后确认玩家手动授权没有被外交恢复清除。
- 英雄死亡、复活、物品、经验和跨关数据行为正确。
- 地图预置、脚本创建、缓存替代、复活、变身、阵营转换和剧情替换可产生的全部战役英雄均已枚举；将目标版本基础单位表与地图对象数据叠加后，其有效 `Stats - Food Cost`（`ufoo` / `fused`）均为 0，实机中英雄出现、复活或替换不会增加已用人口。
- 经济、资源、人口和维修费等全局机制符合《冰封王座》规则，其中维修费须在 50 和 80 人口边界按标准切换。
- 攻击类型、护甲类型及其伤害关系符合《冰封王座》规则，并抽查代表性单位与魔法攻击相关判定。
- 单位、英雄、建筑、技能、科技、升级和物品使用预期的《冰封王座》对象数据；为关卡设计保留的特制数值均有说明。
- 《混乱之治》地图在《冰封王座》数据下新增可训练的英雄、单位或科技必须显式审计和限制；所有参与槽位的固定种族在大厅中不可漂移。
- 胜利、失败和重新开始不会卡住其他玩家；玩家中途退出采用引擎默认行为，不属于自定义验收范围。
- 长时间运行无可复现的不同步或确定性错误。

## 1.31 注意事项

1.31 引入了 Lua、额外原生函数、文件夹地图、自动导入和新的地图数据组织方式。它通常能读取旧地图，但用 1.31 保存后的地图可能无法再被旧版识别。因此 1.31 只用于读取和运行验证，兼容主文件仍由经典编辑环境产生。
